# Matching rules

The decisions TagMender makes when it identifies an album, chooses its release (pressing), tags
it and files it. Every rule has an ID. Code that applies a rule cites the ID in a comment
(`# BAR-1`); its tests carry the ID in their class or test name; the reason shown in the app
may name it. When the code and this file disagree, this file is the intended behaviour and the
code is the bug. A case no rule covers is asked, then added here.

Status: **in code** (implemented, with the test named), **to verify** (believed implemented,
no test traced yet).

Terms: *album* = the work (artist, title, tracks); *pressing* = one release of it (label,
catalogue number, barcode, country, media). *Album known* = tagged with what every candidate
pressing shares (album, artists, titles, original date), without pressing details (release IDs,
label, catalogue number, barcode, media, country).

## Precedence

When rules point different ways, the earlier group wins:

1. Barcode (BAR)
2. Other evidence read off your copy (EVI), the edition your folder names (EDN), box sets (BOX)
3. What the audio and folder say about the media (MED)
4. Your earlier choice (TAG)
5. Source preference (SRC), then country order and ties (TIE)

## Barcode

| ID | Rule | Status |
|---|---|---|
| BAR-1 | A barcode from your copy that matches a release makes that the release, even when the audio could not come from its media (a CD barcode on 24/96 files is still that CD). | in code (`classify`) |
| BAR-1b | A release proven by your scans (its barcode or catalogue number printed on them, nothing on them against it) is filed even below organize_min_confidence when some track lengths differ (a vinyl rip's run-in and gaps), at a score of at least 90 (replace_min_confidence), when the files are the release's tracks (none missing) and at least half their lengths agree. Not with Extra-careful matching. | in code (`plan._files_on_evidence`); tests `BAR1_*` |
| BAR-1a | When your barcode is on several releases (a hybrid SACD listed once as SACD and once as CD), the one whose media can hold your audio is taken. | in code (`classify`, `_yields_to_audio`) |
| BAR-2 | Your barcode on one database's unsure pick beats the other database's sure pick that does not carry it, whatever the Sources preference: the barcode's release is taken. When two entries of that database share the barcode, HF-2 applies. When both picks carry the same barcode, the sure one stands. | in code (`_proof_left_unsure`, `_barcode_taken`); tests `BAR2_*`, `SurePickNotDisputed` |
| BAR-3 | Two barcodes of yours naming two releases: the barcode read on the outer packaging (back cover, box, slipcase, o-card) wins over one on a disc, booklet or inlay. When that cannot be told, HF-2 applies. | in code (`barcode_on_outer`, `_outer_barcode_pick`); tests `BAR3_*` |
| BAR-4 | A barcode on your scans that is on no release in either database, nor sold in the shops (a shop sticker), is ignored. One that was not searched, or whose search failed, still says another pressing. | in code |
| BAR-5 | A barcode printed on your scans beats a different barcode in your files' tags. A barcode only another tagger wrote (TAG-3) is its guess: on a release carrying your folder's catalogue number it differs without making that release another product; on one carrying your exact disc ID likewise, unless a release carrying the tags' barcode has that disc ID too (then the disc ID tells neither apart). When the tags' release ID names a pressing the folder's number rules out, your exact disc ID on the pick says which is right (no hold) only when the tags' release lacks it. | in code (`score_candidate`, `tagger_lift`, scans' barcode as proof, tags' alone weak); tests `BAR5_*`, `TAG3_*` |
| BAR-6 | When your own barcode (or catalogue number) proves the release and the release holds exactly as many audio tracks as your folder, a larger track total in your files' tags (counting a DVD in the set, or another edition) never holds the album back: it is told in the notes. | in code (`match_albums._copy_disagrees`); tests `BAR6_*` |
| BAR-7 | Your copy's own barcode on the release (from your files as ripped, your scans, a cue sheet or booklet; never one another tagger wrote), with every track there, artist and title agreeing and the album itself fitting as BAR-8's (half its lengths or half its track titles), decides the release whatever the track lengths say (a remaster, lengths printed otherwise): neither the lengths nor the score they lower hold it back, as an agreeing catalogue number already excuses them. A barcode on a release none of whose tracks fit by length or title (half of neither) is another album's and decides nothing. | in code (`classify`); tests `BAR7_*` |
| BAR-8 | Your copy's own number proves the release, so nothing else about names holds it back: with your barcode on it, every track there, the artist agreeing and the album itself fitting (half its lengths or half its track titles), a title your tags write otherwise (Guru Guru - UFO, tagged "UFO/ Hinten" by another tagger) and a version your folder does not name (Live & Unreleased) are told in the notes; and a catalogue number printed on your copy (a scan, a PDF booklet - never only typed in notes or a saved page, and whole, never inside a longer one, never the start of one printed on - "SICP 10151~4", "ECM 1064/65", "SRCS-1234-5" - and never joined across a line break; a number the release itself lists with its slash, "2230/31", is still found as "2230 31" or "2230/31") is your own number, as one in your tags or folder name is (Makarski & Jarrett - Bach, ECM 476 4582: 89.6). | in code (`classify`, `catno_printed`); tests `BAR8_*` |
| BAR-9 | A MusicBrainz release that lists no barcode, whose Discogs releases (the ones it links to, every one of them scored) all carry another barcode than your copy's own, while other Discogs releases carry yours, is that other product - never your pressing, whatever disc ID it carries (TOC-1 proves the album on the disc, not which pressing of it; a club edition shares the retail CD's master): MusicBrainz's pick is unsure, and the pressings carrying your barcode decide, by the tie rules (Robin Trower - Bridge Of Sighs: MusicBrainz's BMG club edition, its Discogs entry's "D131674", against the retail EAN 0724352081127 on your back cover: Discogs's US retail CD). | in code (`match_core._yields_to_linked_barcode`, `combine`); tests `IDEM_ClubEditionAgainstYourBarcode` |
| BAR-10 | A barcode is written as its digits ("72435-20811-27" -> "724352081127"): the form a scanner reads and the databases' barcode searches find exactly. Only digits with spaces, dashes or dots of a barcode length (8, 12, 13, 14 digits) are rewritten; any other text stays. | in code (`engine.barcode_digits`, `discogs_parts`); tests `test_v0848_barcode_digits` |
| BAR-11 | The barcode written is a barcode: of a Discogs release's Barcode entries, the first whose digits make an EAN-8, UPC-A, EAN-13 or GTIN-14; the number printed under the bars that Discogs often lists first as "Text" ("88561-1024-2", the catalogue number) is written only when no entry is a barcode. Matching compares every entry, as before. | in code (`plugins_builtin/discogs/discogs_mapping.py`); tests `BAR11_*` |
| BAR-12 | MusicBrainz's sure pick carries your copy's barcode but not your disc IDs, while another MusicBrainz release lists no barcode, carries every disc ID of your copy (TOC-1: each disc's ID on that disc of the release), fits at least as well, and links only Discogs releases carrying your barcode (every one of them scored); and Discogs's own pick is one of the releases it links to, never one the barcode's MusicBrainz release links to - sure, or held (on a tie, or for any other doubt) only when something of your copy (a matrix, a catalogue number, what your scans show; never its place in the tie, nor the disc ID it inherits from that very entry) puts it before each other entry carrying your barcode. Then that release is an entry of the same product whose barcode was not typed in, Discogs's evidence and your disc IDs agree on it, and it is taken, Discogs's pick paired with it (Univers Zero - Heatwave, Cuneiform RUNE 9: MusicBrainz a74c2f10, your disc ID, linking Discogs 580070 - the pressing your scans' matrix names - with barcode 045775000923, against 958886df carrying that barcode). A disc ID alone never decides it: which entry someone submitted it to names no pressing (TOC-3, BAR-9). The barcode still names the product (BAR-1): an entry listing another barcode, linking a Discogs release that lists none or another, linking none or one not scored, two such entries, one disc's ID of several, or Discogs's pick being another pressing, keeps the release carrying your barcode; that release carrying your disc IDs too stands. | in code (`match_core._disc_id_twin_of_barcode`, `combine`); tests `BAR12_*` |
| BAR-13 | Your copy's own code (a barcode from your files as ripped or your scans, a catalogue number from your tags, folder name or rip notes; never one another tagger wrote, one only typed in notes, nor one OCR merely found) on an entry whose track list is too sparse to compare - no lengths at all, or fewer tracks than your files (a box's discs listed in part) - names the pressing when a full entry of the same album fits every track and length but lacks your code: the album is proven by the full entry, the pressing by your code. Discogs entries only (a MusicBrainz release's IDs name its own tracks: one listing too few is not tagged from another's). Same album: the same master - or, where an entry names none, the same title and artist -, the same number of discs, and the sparse entry's track titles (80% at least) the full one's. The sparse entry is then compared with the full entry's tracks and lengths, and tagged from them: each file its track of the full entry - its title, track artist, numbering and per-track credits are the full entry's; the release's own IDs, label, number, barcode, date, country, notes, album credits and its discs' format stay its own. The same when you choose the sparse entry yourself (its master's versions are read for the full entry). Never for a list of fewer than 3 tracks; only when it is the one entry carrying your code that your copy's hard evidence does not rule out (a barcode of yours that differs, a rip log dated before it came out, a format your files cannot be; a weaker clue against an entry - a country your scans or folder name give, your tags' media, a packaging or matrix - does not, since a sparse entry escapes those by listing nothing): another entry carrying it - of any track count, disc count or master, with lengths or without - leaves the pressing open, since one number is often an original's and its reissues' and a pressing of your number listing its own lengths, a few typed off the sleeve, is never outranked by another's tracks; never when anything of your copy argues against it (a barcode of yours that differs, a rip log dated before it came out - DAT-3 -, the folder name or scans, a format your files cannot be), nor when the full entry carries your code too. The other database's sure pick of that album (same title, artist, track and disc count) that carries no code of yours, nothing of your copy behind it but your disc ID (TOC-3: the disc, not the pressing) and the format, is another pressing: unsure, so the code's pressing decides, and it is never written beside it as its twin (Neil Young - Archives Vol. II, folder "(Reprise 093624899051)", rip logs of 2020: Discogs 16262491, the 2020 limited box, 131 tracks without lengths, over Discogs 17690677 and MusicBrainz 3796a182, the 2021 retail box 093624926214 with your disc ID; MusicBrainz lists no entry of the 2020 box). | in code (`match_core.code_twins`, `_yields_to_code_twin`, `engine._identified` / `discogs_parts` tracks_det); tests `test_v0868_bar13_code_twin` (`BAR13_*`) |
| CAT-1 | An SACD's audio format written in a folder name or album tag ("DSD64", "DST64", "DSD128", "DXD", "PCM", "MCH", "ISO") is never a catalogue number: it is not searched, and never "on none of these pressings" (Blood, Sweat & Tears: "[SACD DSD64 2ch Rip 24bit 352khz]" held five albums back). | in code (`match_core._NOT_CATNO_WORD`); tests `CAT1_*` |
| CAT-2 | A catalogue number in three groups of digits written in a folder name ("[A&M_75021 5350 2]", "75021-5350-2", "31454 0123-2": A&M, PolyGram and Universal US CDs, 5 + 4 + 1 digits) is read as that number; an underscore in a folder bracket stands for a space (Temple Of The Dog, left album only with its number unread). | in code (`match_core.catno_hints`); tests `CAT2_*` |
| CAT-3 | A CD or LP label code in capitals followed by one digit, the whole of its comma-separated part of a folder bracket ("[2009.03.23, RHEADCDX 1]", "[XLCD 1]"), is read as a catalogue number: 4-12 letters ending in CD or LP and at most two letters more. Words ("ANTHOLOGY 2"), disc formats and editions ("HDCD 1", "XRCD 2", "UHQCD 2", "SHMCD 1", "MFSL 2") and disc, volume or part numbers ("CD 1", "Disc 1", "Vol 1") never are. Such a number is your copy's own ("your number is on none of these pressings", a release lacking it) only when some release carries it; like every folder number it counts against a release only then. | in code (`match_core.catno_hints`, `cat3_hint`, `cat3_own`); tests `CAT3_*` |
| CAT-4 | A label's letters written in front of a catalogue number ("GUN 079" for "079", "MAS CD0540" for "CD0540") name the same number only when it has no label letters of its own, or only a format word ("CD"): "TFCK 87128" (a Japanese disc) is not "CK 87128" (a US one; Judas Priest - Metalogy, whose rip logs name the US discs CK 87127-87130). | in code (`match_core.catno_same`); tests `CAT4_*` |
| CAT-5 | When the catalogue number your folder, tags or rip logs name is on none of the releases, only proof decides; a catalogue number printed on your copy (a scan or booklet, BAR-8 - never only typed in notes) is proof, as your barcode is: Judas Priest - Metalogy, whose logs type the US discs' CK 87127-87130 while the box prints its own C4K 87126. | in code (`match_core.classify`, the unlisted-number check); tests `CAT5_*` |
| CAT-6 | A catalogue number a found Discogs release lists that your scans print (BAR-8: whole, on a scan or booklet; letters and digits, 5+ characters) and no search asked for yet is searched with the artist, once every step that finds releases is done, so the other pressings sharing it are compared too. The scan reading leaves a label's letters and one digit alone ("CDCCR 3", which "TRACK 1" resembles); a release found by title can still carry it (Creedence Clearwater Revival - Chronicle, Volume Two: four Discogs releases are CDCCR 3, the title found one). | in code (`match_albums.printed_catnos`, `printed_catno_step`); tests `CAT6_*` |
| RET-1 | What a Discogs search by your copy's own barcode or catalogue number finds is always fetched and compared - never cut by the ranking by title and year that picks which other finds are fetched (Rick Wakeman - Zodiaque: the retail CD 5459861, found by both, ranked below 1988 title-only finds and never compared). Not when that search found more than six releases: a number that many share names no pressing. | in code (`match_albums.discogs_search`, `RET_CODED_MAX`); tests `RET1_*` |
| CLB-1 | A club edition (Discogs format "Club Edition") lists the mark printed on its sleeve ("CRC" on the back cover: Columbia House). When your scans were read well enough to show this release's barcode or catalogue number and the mark is not on them, that counts against it; a release carrying your barcode that nothing argues against, fitting your tracks as well and behind only by the year (a folder's year is the album's, not the pressing's), is taken instead. A scan not there, or read too poorly to show the barcode or number, says nothing either way. | in code (`match_albums.discogs_club_marks`, `match_core.club_mark_missing`, `classify`); tests `CLB1_*` |
| YR-1 | A folder's year with no pressing named beside it ("1988 - Zodiaque", not "[2004 RM]") is the album's year: most libraries name folders by the original release. A reissue agrees with it through its album's first release - MusicBrainz's release group's first date, Discogs's master's year (asked only when the pressing's own year differs) - never through a later "original" (MusicBrainz: its release group's first release, asked once per album when needed). Ties still order by the distance to the pressing's own year; a pressing year in the folder is compared with the pressing's year, as before. | in code (`match_core.score_candidate`, `match_albums.mb_candidate` "original_year", `_master_years`); tests `YR1_*` |
| PRV-1 | What TagMender wrote does not corroborate itself: its own TAGMENDER_SOURCE (the shop page its web search found) is no link the files came with and is not read as one (it would prove the release that page leads to); ISRCs its job wrote from the release it chose are read as they were before the job, like the pressing fields (REP-1), so they never prove that release's recordings. The release IDs it wrote stay as written: TAG-1 decides what they keep. | in code (`match_albums._source_clues`, `read_file`, REPLAN_FIELDS "isrc"); tests `PRV1_*` |
| CTY-1 | A release country that is no country - neither a code nor a country's name - but a word the files also carry as their label, comment or encoder (a rip group's mark, "PMEDIA") goes when the album is tagged and its release names no country to replace it - only where the profile's level writes a release country (never at Basic, never a field level_fields drops, never on an album only or Partial). A mark is one word in capitals; a country code, a known country name or any mixed-case name stays, as does what a preserve, lock or fill_missing policy (your tagger settings' "Preserve these tags") keeps. | in code (`plan._junk_country`); tests `CTY1_*` |
| CTY-2 | A country your scans say the copy was made in is nothing against a release whose own notes say its parts were made there ("Made in West Germany (Booklet)", "Made in United Kingdom (CD Face)": Discogs 25736467, filed under UK). It is no clue for it either: one booklet often came with several pressings. | in code (`match_albums.discogs_candidate` `notes_made_in`, `match_core.countries_made_in`, `pressing_clues`); tests `CTY2_*` |

## Evidence from your copy

| ID | Rule | Status |
|---|---|---|
| EVI-1 | Weight of evidence, strongest first: barcode > catalogue number > disc ID / matrix (runout) > label or country printed on the scans > folder name > country order. | in code (`CLUE_WEIGHTS`); tests `EVI1_*` |
| EVI-2 | Evidence shared by every candidate (a catalogue number on all editions) tells nothing apart; so does a release country (or media) in your tags that none of the tied pressings has (another tagger's GB on an album out only in DE and RU): it never outweighs your disc ID or stops the country order. A download entry that lists no catalogue number is unknown, not different - also when your scans (a CD sleeve bundled with a download) print another pressing's number. | in code (`_weigh`, `choose_pressing`); tests `ScansNumberAgainstAnUnlistedOne`, `EVI2_*` |
| EVI-3 | Text read off the scans (for example "Made in EU") beats the country order. | in code |
| EVI-4 | Poor OCR (few words of artist or title read) never lowers the confidence: scans only add evidence. | in code (`score_candidate`, OCR only adds); test `EVI4_*` |
| EVI-5 | When your own barcode is on every tied pressing, what your audio says against them all alike ("hi-res audio cannot come from this CD": a 24/96 download carrying the CD's UPC) tells none of them apart and does not stop the tie-break (BAR-1: the barcode names the product whatever the audio). Without your barcode on them all, it stands (an unlisted download: Album only). | in code (`choose_pressing`, `_MEDIA_AGAINST`); tests `EVI5_*` |
| EVI-6 | When your evidence (a catalogue number on your scans, ...) is on some tied pressings only and does not single one out, the tie-breaks (one pressing listed twice, the country order, the original date) choose among those, never among the others: Raising Sand's scans name Rounder 1166190752, on the US (listed twice) and ZA entries, not the CA one. | in code (`_choose_pressing`, `_country_listed_twice`); tests `EVI5_EVI6_*` |
| EVI-7 | A label named as the album's artist (an artist's own imprint, such as Discogs's "Tangerine Dream" label on a promo) is no clue read off the scans: the artist's name is printed on every sleeve (Tangerine Dream - Winter In Hiroshima: the promo was picked over the retail CD carrying your disc ID). | in code (`pressing_clues`); tests `MED10_*` |
| EVI-8 | Two entries with the same label, catalogue number and barcode are one pressing listed twice only when their matrices allow it: when each lists a matrix for its audio discs and no two share a numbered part (runs of 5 digits or more, spacing and dashes ignored, the catalogue number and barcode left out, one run holding another counted as shared; a video disc's matrices, which an entry may list alone, never compared), they were pressed apart and are two pressings, so "the fuller entry" never chooses between them (Opeth - Blackwater Park, Legacy Edition: Discogs 2261489, Arvato "54044125/88697655822-1", and 10001697, Sony DADC "A0102309767-0102"). The matrix your disc shows decides; without it the tie stays. | in code (`match_core._matrices_disjoint`, `same_pressing_listed_twice`); tests `test_v0864_pilot2` (`EVI8_*`) |
| EVI-9 | The matrix your disc shows names the pressing among those sharing its catalogue number or barcode. When the disc ring itself reads the matrix of exactly one release (never a sleeve's page text: then nothing is left out), and it fits the album with nothing of your copy against it, the releases carrying its number or barcode that list a matrix of their own your scans do not show are left out, however well their listed lengths or country fit (Creedence Clearwater Revival - Chronicle, Volume Two: four Discogs releases are CDCCR 3; the disc reads Mayking's, 25736467, whose lengths are the sleeve's, over Sonopress's 38540601 listing the rip's own). Never against your copy's own proof: one carrying your barcode or exact disc ID stays unless the matrix match carries it too (BAR-1). One listing no matrix stays (it may be the same pressing, undocumented), and so does one whose matrix is only its catalogue number again; nothing is left out when your scans read two releases' matrices. One whose own plant or code the ring reads stays too - a plant's name of 3+ letters ("EMI", "PMDC"), even one the match lists as well (two PDO pressings are not told apart by "PDO"), or a code of 4+ characters. Those left out are told why. | in code (`match_core.matrix_drop`, `classify`); tests `EVI9_*` |
| DAT-3 | A rip log of your files carrying the date it was made sets a ceiling: a pressing whose own release date is in a later year cannot be the disc that was ripped ("your rip log is dated 2005; this pressing came out in 2012"). It only chooses among the releases found: nothing is ever held for the date alone. The date is an EAC log's first line ("EAC extraction logfile from 27. August 2005, 15:28", in any of EAC's languages, CUERipper's too; never EAC 1.x's "Exact Audio Copy V1.0 beta 3 from 29. August 2011", the program's build) or an XLD log's ("XLD extraction logfile from 2008-09-24 ..."); a checker's log (auCDtect, audiochecker) has none. The log must be proven to be of your files: its TOC fits them (TOC-1's fit), or, without a TOC (older EAC), a CUETools report in the folder confirms its CRCs; a log merely naming files like yours may be another rip's of the same album and sets no ceiling. A log dated before the album's first release (the candidates' release group or master year, else your folder's or tags' year) is misdated and rules nothing out. Years only (a release's month or day may be unknown; a rip in the year a pressing came out may be of it), the pressing's own date only (MusicBrainz's release date, Discogs's released year; never the release group's or master's first date), and a release without a date is unknown, not later. Like the folder name's word, it leaves a later pressing out only for one not later (or undated) of the same album that fits with nothing of your copy against it (no other clue against it, no format your audio rules out: an earlier LP never takes a CD rip's place), and what your copy proves of the later one must be on that one too: your barcode (BAR-1) - only for one carrying it too (pressings sharing your barcode and catalogue number, Pekka Pohjola - Flight Of The Angel: the 2002 remaster, MusicBrainz 1ec067b6, not the 2012 Finnish entry 192d6570); your exact disc ID (TOC-1) or your own catalogue number - only for one carrying either of those or your barcode. A pressing left out gets the clue against it; one not left out (every release found came out later, a guard, a misdated log) stays as without the log, the pick told why in its notes ("every release found came out later: the log's date or the database may be wrong"). | in code (`match_albums.log_date_year`, `rip_log_year`; `match_core.rip_date_against`, `rip_date_drop`, `classify`); tests `test_v0865_dat1_rip_date` (`DAT3_*`) |
| TOC-1 | Your disc's table of contents (from the rip log or cue sheet) fits your files to the sector on every disc, and MusicBrainz has each of those disc IDs attached to the release: the release is proven though the lengths it lists differ (typed or rounded) and though the folder names the artist otherwise (credited as the database does). Every disc of your files needs its TOC, and each disc ID must be on that disc of the release. Its title must agree with yours (and, when the artist is credited otherwise, its track titles too), three tracks or more, the track counts the same; a fuzzy disc match or a log of another rip is no proof. Filed on it below organize_min_confidence when it is clear of the runner-up (not when pressings sharing the disc ID tie and the country order chose), never with Extra-careful matching. | in code (`match_core.toc_lengths`, `classify`, `plan._files_on_evidence`); tests `TOC1_*` |
| TOC-2 | A CUETools database (CTDB) link to a Discogs release is no proof of your disc. CTDB finds Discogs releases by a near match of lengths and gives each a relevance score (every Discogs entry it sends carries one, 100 included): "a CD of about these lengths". Such a link is told ("disc TOC (fuzzy)") and its release is still fetched (your tags' links first, then near matches by relevance, best first), but it proves nothing. So a Discogs release gets the disc ID clue only through MusicBrainz: when a MusicBrainz release carrying your exact disc ID links it, it is that disc's entry - it gets the clue and is fetched when the search missed it (the most relevant first, four at most); one linked only by a fuzzy match gets nothing. (A Discogs entry without a relevance score, which CTDB does not send, would count as exact: older test fixtures write them.) Among Discogs pressings the clue still tells none apart (a disc ID proves the album on the disc, not which pressing). When MusicBrainz is sure of a pick your folder name contradicts ("folder name says JP") and Discogs's held pick fits the folder (its country or number) and has a CTDB near-match link (the "disc ID" this rule took from it), the two are disputed, never MusicBrainz's taken - not when MusicBrainz's pick carries your copy's barcode or your own catalogue number and Discogs's does not, and not when Discogs's pick has no CTDB link (a sure MusicBrainz pick by your exact disc ID stays sure against unlinked Japanese entries, as before). (Radiohead - Pablo Honey box: CTDB's near matches gave the US box the disc ID, which only the UK box carries.) | in code (`match_albums.toc_releases`, `toc_discogs_order`, `disc_id_discogs`, `with_discogs_ids`, `match_core.file_clues`, `_folder_fit_disputes`); tests `TOC2_*` |
| TOC-3 | MusicBrainz's sure pick carrying your exact disc ID overrules a Discogs pick of another pressing only when nothing of your copy speaks against it: when your folder name (its country, its format) or your scans (the country they print) say something against MusicBrainz's pick that they do not say against Discogs's, the two are disputed instead (HF-2: the database preferred in Sources then decides, with the dispute noted). A disc ID that several pressings share proves the disc, not the pressing (Pink Floyd - The Dark Side Of The Moon, Immersion box, "USA, Mexico": the disc ID is attached to the GB entry; the US/Canada pressing, Discogs 3137117, is kept). | in code (`match_core.mb_overrules`, `_against_only`); tests `test_v0864_toc3_against` (`TOC3_*`) |
| LEN-1 | A release that lists EVERY track a few seconds short of your files (none more than 1 s longer, nor shorter by more than 4% of the track and 10 s, most of them short at all, four tracks or more) agrees on lengths: times copied off a sleeve. Another edit or version is not short on every track. | EDT-1 | While a look-up runs, an album it is not looking up can be edited (cover, tags); one it still has in hand waits, and you are told. Clear Done takes Done albums out of the list while work runs (CLR-1). | in code (`Overview.album_busy`, `_take_out`); tests `EDT1_*`, `CLR1_*` |

## Mixed folders

| ID | Rule | Status |
|---|---|---|
| MIX-1 | Two albums or versions (stereo and 5.1) in one folder: if one release in the databases holds both (one catalogue number, e.g. disc 1 stereo and disc 2 5.1), they are filed as that one album, with disc number and disc subtitle tagged. If they are different releases, each is split and filed in its own folder. If neither is known on its own, a release holding both versions is looked for first: that is the answer when found. Disc number and disc subtitle are always tagged; an inferred disc subtitle names format and layout ("SACD Stereo", "Blu-ray 5.1", "CD"). | in code (`engine.version_subtitles`); tests `MIX1_*` |
| MIX-2 | A media tag naming a channel layout ("Stereo", "5.1") makes a disc a version of another only when another disc of the album names another layout; one disc whose CD media tag says "Stereo" (Discogs's format "CD, Album, Limited Edition, Stereo") is the album, never a version folder whose disc must be proven. A lone disc naming its mix otherwise (an SACD area, "Hybrid SACD (SACD layer, 6 channels)", "DVD-Audio (5.1)") stays a version. | in code (`match_albums.version_discs_by_tags`); tests `IDEM_OneStereoDiscIsNoVersion` |
| MIX-3 | Folders named after their channel layout ("2ch_SACD/" and "6ch_SACD/") whose files are tagged as one album by one artist apart from closing marks made only of format, layout, audio or edition words, and a catalogue number beside them ("[SACD 2ch DSD64 24bit 352khz]", "[HD]", "[2015 Remaster]", "(5.1)", "[1980 Vinyl Rip]", "[SACD AFZ5 198 2ch DSD64]") - "Child Is Father To The Man [SACD 2ch DSD64]" beside "Child Is Father to the Man [HD]", one version tagged before the other - are still versions of one disc of that album: grouped as one album, read with the set folder's name, its scans and rip log. Titles that differ otherwise ("[Live]", "(Volume 2)", "(Mono)" against "(Stereo)", "(2)" against "(3)") are two albums. | in code (`engine._one_album_titled`, `_without_version_marks`, `version_dirs`, `albums_in`); tests `EDI_version_folders_*` |
